# CRM INTEGRATION — СМЛаб

_2026-10-03. Статус: **CRM AUDIT — COMPLETED · CRM INTEGRATION — BLOCKED**._

## 0. CRM известна — интеграция заблокирована

CRM клиники — **«МедЦентр»**: самописное приложение на **Python / FastAPI / Jinja2 / SQLite** для персонала в локальной сети (статический аудит копии 2026-10-03 — [`CRM_AUDIT.md`](./CRM_AUDIT.md)). **Внешнего API нет**, большая часть действий без проверки входа, в копии — реальные персональные данные.

**CRM Integration = BLOCKED** до выполнения как минимум:

1. security remediation P0 в CRM — [`CRM_SECURITY_REMEDIATION.md`](./CRM_SECURITY_REMEDIATION.md);
2. API или серверный адаптер к CRM по требованиям — [`CRM_API_REQUIREMENTS.md`](./CRM_API_REQUIREMENTS.md);
3. тестовая среда;
4. обезличенная тестовая база;
5. модель расписания и свободных слотов;
6. решение по авторизации пациентов и смс-провайдеру.

Для владельца — [`CRM_OWNER_SUMMARY.md`](./CRM_OWNER_SUMMARY.md), вопросы — [`CRM_OWNER_QUESTIONS.md`](./CRM_OWNER_QUESTIONS.md).

Разделы ниже по-прежнему описывают **требования сайта**. Адреса запросов и форматы CRM здесь не фиксируются, пока API не реализован: существующие HTML-маршруты интерфейса персонала CRM — не API и для сайта не используются. Реальные данные CRM в СМЛаб не импортируются.

## 1. Current frontend architecture

```
UI (страницы, компоненты)
  → сервисы (src/services/*)            ← контракты-интерфейсы, UI знает только их
    → реализация по DATA_SOURCE          ← src/services/config.ts
       mock: код и браузер (сейчас)
       crm:  ещё нет → сборка останавливается с понятной ошибкой
```

| Контракт | Файл | Что делает | Где вызывается | MOCK хранит в |
|---|---|---|---|---|
| `DataSource` | `services/data-source.ts` → `source.ts` | Каталог: услуги, направления, врачи, анализы, программы, акции, клиника | **Только сервер** (страницы, `services/*.ts`) | Код (`src/data/mock/`) |
| `BookingService` | `services/booking/` | Расписание, резерв, создание и перенос записи | **Браузер** (запись, перенос) + сервер («ближайшее время») | sessionStorage (резерв), записи — в хранилище записей |
| `AuthService` | `services/auth/` | Код подтверждения, сессия, профиль | **Браузер** (`lib/auth-session.ts`) | localStorage |
| `AppointmentService` | `services/appointments/` | Список, детали, правила, отмена | **Браузер** (кабинет) | localStorage |

Правила, которые **уже** соблюдаются и не должны нарушаться интеграцией:

- UI не импортирует MOCK-данные и не обращается к `localStorage` / `sessionStorage` напрямую (проверено 2026-09-27): только через `src/lib/*` и сервисы.
- Ожидаемые бизнес-исходы — результат `{ ok: false, reason }`; сбои инфраструктуры — `ServiceError` с кодом (`services/errors.ts`). Сырой ответ CRM в компоненты не попадает.
- Экраны умеют: загрузку, пустое состояние, ошибку и повтор (каталоги — `app/error.tsx`; запись — расписание, резерв, подтверждение; вход — отправка и проверка кода; кабинет — список, запись, отмена, перенос, профиль).

## 4. Auth / patient requirements

Два разных вопроса — не смешивать:

| | Patient identity | Authentication |
|---|---|---|
| Что это | Кто пациент в CRM: id, телефон, имя | Как доказать, что телефон принадлежит пользователю |
| Сейчас (MOCK) | localStorage: телефон → профиль | Фиксированный код `11111` |
| Нужно выяснить | Хранит ли CRM пациентов; поиск по телефону; создание; обновление; какой id использовать; дубли по телефону | Отправляет ли CRM код сама; нужен ли отдельный смс-провайдер; срок жизни кода; ограничения попыток |

Требования production (не зависят от CRM):

- **Сессия — на сервере**: httpOnly-cookie, выданная сервером Next.js после проверки кода. Сейчас сессия в localStorage — это демо.
- **Доступ к записям — проверка на сервере**: сервер берёт patientId из сессии, а не из запроса браузера. Сейчас защита кабинета только клиентская (`AccountGuard`).
- Лимиты на отправку и проверку кода — на сервере / у провайдера.
- `NEXT_PUBLIC_DEMO_MODE` и тестовый код удаляются при подключении реальной авторизации (PD-26).

## 5. Availability requirements

Контракт frontend (`BookingService.getAvailability`, `getUpcomingDays`): для цели (врач + услуга или процедурный кабинет) и периода — дни со списком времени `HH:MM` и признаком «свободно».

Нужно от CRM:

- свободное время врача **с учётом услуги** (длительность приёма может зависеть от услуги);
- свободное время процедурного кабинета (часы забора могут отличаться от приёма врачей);
- шаг и длительность слотов;
- **часовой пояс** расписания — `Europe/Moscow` (PD-30, `clinic.timezone`); нужно знать, в каком поясе CRM отдаёт и принимает время (вопрос 18);
- горизонт записи (сейчас `horizonDays` = константа MOCK);
- актуальность: как быстро занятый слот пропадает из выдачи.

Нагрузка: «ближайшее время» на карточках врачей сейчас считается по одному запросу на врача. Нужен ли пакетный запрос «ближайший свободный слот для списка врачей» — вопрос к CRM (лимиты запросов).

## 6. Reservation requirements

Сейчас резерв на 5 минут (PD-02) **имитируется в браузере** — это не защита от двойной записи.

Нужно выяснить у CRM:

| Возможность | Если есть | Если нет |
|---|---|---|
| Hold / резерв слота | id резерва, срок, снятие, подтверждение резерва записью | **Production gap**: либо запись сразу без резерва (таймер 5 минут в UI убирается или становится информационным), либо резерв в своём серверном слое |
| Атомарная проверка конфликта при создании | «занято» при создании записи | Двойная запись возможна — нужно решение CRM |
| Срок резерва | берём из CRM | правило PD-02 (5 минут) не может быть гарантировано |

Производственную блокировку **нельзя** реализовать только во frontend.

## 7. Appointment requirements

- Список записей пациента, запись по id (только своя), статусы: предстоящая, завершена, отменена. Сейчас «Завершена» вычисляется по времени в браузере — лучше получать статус из CRM.
- Создание, отмена, перенос — W3–W6.
- Правила отмены и переноса: `canCancel`, `canReschedule`, `restrictionReason` — **PRODUCTION RULE UNKNOWN** (PD-06). Демо-правило «будущую можно, прошедшую и отменённую — нельзя» не является правилом клиники.
- Перенос: меняются только дата и время; должен быть атомарным (прежнее время освобождается ровно тогда, когда занято новое).
- Стоимость записи: какую цену CRM считает итоговой (цена услуги у врача; сумма анализов; скидки акций) — правило CRM.
- Идемпотентность создания записи (повторный клик, повтор после таймаута) — вопрос к CRM.

## 8. Integration boundary (Next.js)

```
Каталог (только чтение):
  Server Component → DataSource (CRM-реализация) → CRM        ← секреты на сервере

Запись, вход, кабинет (браузер):
  Client Component → сервис (CRM-реализация: вызов сервера)
    → Next.js server (Route Handler или Server Action)
      → серверный CRM-клиент (секреты, сессия, patientId из cookie) → CRM
```

- Интерфейсы сервисов **не меняются**: UI остаётся как есть, меняется только реализация за `selectImplementation` (`services/config.ts`).
- Серверный CRM-клиент — модуль с `import "server-only"`, секреты — переменные без `NEXT_PUBLIC_`.
- Для публичного каталога возможно кеширование (revalidate) — зависит от лимитов CRM и того, как часто меняются цены.
- **Не реализовано сейчас** намеренно: без документации CRM любой клиент, маршрут или DTO были бы выдумкой.

Mapper layer: создаётся вместе с CRM-реализацией — `CRM DTO → mapX() → доменная модель`, по файлу на сущность, **только** для реальных ответов CRM. Сейчас мапперов нет: нечего сопоставлять.

## 10. Environment variables

См. `.env.example`.

| Переменная | Где | Секрет | Назначение |
|---|---|---|---|
| `DATA_SOURCE` | сервер и браузер (через `next.config.ts`) | нет | `mock` (по умолчанию) или `crm`. Неизвестное значение и `crm` без реализации останавливают сборку |
| `NEXT_PUBLIC_DEMO_MODE` | браузер | нет | подпись «Демо-код» (PD-26), удалить с реальной авторизацией |
| `NEXT_PUBLIC_SITE_ENV`, `NEXT_PUBLIC_SITE_URL` | сервер и браузер | нет | окружение и домен — см. `PRODUCTION_READINESS.md`. production требует `DATA_SOURCE=crm` |
| `CRM_BASE_URL`, `CRM_API_KEY` | только сервер | **да** | заготовка; точные названия — по документации CRM |

Режимы: разработка и демо — `DATA_SOURCE=mock`; production — `DATA_SOURCE=crm` после появления CRM-реализаций всех четырёх сервисов.
