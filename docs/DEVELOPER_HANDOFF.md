## 4. Booking и авторизация

Проверено по всем четырём booking-файлам: сценария «заявка + звонок администратора» нет нигде, все четыре экрана заканчиваются состоянием «Запись подтверждена» / «Вы записаны».

### Запись к врачу

```
Услуга → Врач → Дата и время → Данные / авторизация → Подтверждение
```

**Стартовый шаг зависит от точки входа:**

| Точка входа | Стартовый шаг | Уже отмечено |
|---|---|---|
| Общая кнопка «Записаться» (шапка, главная) | 1. Услуга | — |
| Со страницы услуги | 2. Врач | Услуга |
| Со страницы врача | 1. Услуга | Врач |
| С услуги в профиле врача | 3. Дата и время | Услуга, Врач |

### Запись на анализы

```
Выбранные анализы → Дата и время → Данные / авторизация → Подтверждение
```

Та же модель без шага выбора врача.

### Авторизация

```
Телефон → OTP → авторизован
```

Отдельной регистрации с паролем нет. Экраны `Booking-Doctor`, `Booking-Labs` и `Cabinet-Login` используют одни и те же компоненты поля телефона, ячеек OTP и строки повторной отправки — **в коде это тоже должен быть один общий компонент, а не три копии.**

### ⚠️ Смена номера телефона — FUTURE / PRODUCT ASSUMPTION

На макете `Cabinet-Profile` есть режим смены номера через повторный OTP. **Это не подтверждённая функция MVP.**

На текущем этапе:

- в профиле **отображается** текущий номер пользователя;
- функциональная смена номера **не реализуется**;
- дополнительная auth-логика ради неё **не создаётся**.

Возврат к вопросу — после подключения реальной авторизации. Состояние «режим смены номера» исключено из списка обязательных states экрана «Профиль» (раздел 3).

## 6. ⚠️ Что на макетах статично, а в коде должно быть живым

Главный источник ошибок при переносе статичного макета в код.

| В макете | В коде должно быть |
|---|---|
| Sticky CTA — статичный блок с пунктирной рамкой и подписью | Настоящий `position: fixed` / `sticky` у нижнего края, поверх контента, **не перекрывающий последнюю карточку списка** |
| Панель выбранных анализов — статичный демо-блок | То же самое |
| Modal / Bottom Sheet — блок, встроенный в поток страницы | Настоящий диалог: затемнение фона, ловушка фокуса, закрытие по Esc и по клику вне |

**Ещё из аудита дизайна:**

- На каталогах услуг и врачей используются **локальные** версии empty/loading-состояний вместо общих. Визуально сведены, но код не объединён — при вёрстке консолидировать в один компонент.
- Футер на всех экранах собирается из общих частей — **не заводить локальных копий разметки**.
- Промежуточные ширины (планшет) **не макетировались**. Адаптация между 390 и 1440 — на разработчике, по тем же принципам.

## 9. Данные: FACT и MOCK

**FACT** — можно выводить как сведения о клинике: название **Смлаб**, **один филиал**, адрес **Западный обход, 42к2**, розово-голубой фирменный стиль.

**MOCK** — всё остальное на макетах: врачи, цены, анализы, акции, тексты услуг.

### Правило отображения MOCK

**MOCK — это внутренний статус данных для разработки.** В пользовательском интерфейсе **никаких видимых бейджей или надписей «MOCK» быть не должно.**

Разделение обеспечивается на уровне кода и документации:

- mock-данные лежат в **отдельных изолированных файлах**, помеченных как временные, чтобы удаляться одним действием при подключении CRM;
- в документации явно указано, какие данные mock, а какие подтверждены;
- mock-данные **не выдаются за реальные сведения клиники** ни в текстах, ни в метаданных страниц.

**Расхождение, отмеченное в аудите дизайна:** цена «Специалист №2» разъезжалась между экранами (3800 ↔ 2900 ₽), приведена к 2900 ₽. Это исправление внутри демо-данных, а не факт о клинике.

## 10. Контраст и semantic tokens

Палитра Design v1 проверена на WCAG. Найдено 5 групп нарушений, **все исправлены 2026-09-24 через слой semantic tokens** — базовая палитра при этом не менялась. Полные результаты: [`./CONTRAST_AUDIT.md`](./CONTRAST_AUDIT.md).

### ⚠️ Правило вёрстки

**В компонентах использовать semantic-токены, а не примитивы палитры.** Примитив напрямую — только там, где подходящего semantic-токена нет.

Это не стилистическое пожелание: пять сочетаний примитивов не проходят WCAG, и semantic-слой существует именно для того, чтобы их нельзя было применить по ошибке.

| Задача | Использовать | Не использовать |
|---|---|---|
| Ссылка на белом фоне | `--color-text-link` | — |
| Ссылка на `surface` / `blue-50` / `blue-100` | `--color-text-link-on-tinted` | ❌ `--blue-600` (4.13–4.48) |
| Placeholder в поле ввода | `--color-text-placeholder` | ❌ `--ink-400` (3.01) |
| Граница input / select / checkbox / time slot | `--color-control-border` | ❌ `--line-200` (1.21) |
| Разделитель, граница карточки | `--color-border-decorative` | — |
| Кольцо фокуса | `--color-focus-ring` | ❌ `--blue-500` (2.73–2.96) |
| Primary CTA | `--color-cta-bg` + `--color-cta-text` | ❌ `--pink-600` с белым текстом (4.11) |
| Декоративная розовая заливка | `--color-decorative-pink` | — |
| Текст статуса | `--color-text-success` / `-warning` / `-error` | ❌ базовые `--success` / `--warning` |
| Иконка статуса | `--color-icon-success` / `-warning` / `-error` | — |

### Два остаточных вопроса

Оба описаны в `CONTRAST_AUDIT.md` и требуют проверки **при вёрстке конкретных экранов**:

1. **Граница поля на подкрашенной секции** — `--color-control-border` даёт 3.01 против белого интерьера поля, но 2.85 против `surface` снаружи. По строгому прочтению WCAG 1.4.11 это не проходит.
2. **Белый текст на заливке `success`** — 4.14 при норме 4.5. Проверить состояние «Запись подтверждена» в `Cabinet-Dashboard` и `Booking-*`: если там белый текст на зелёной заливке, нужна замена.

## 13. Публичный каталог — решения и открытые вопросы

Реализовано 2026-09-25: «Услуги и цены», страница услуги, «Врачи», страница врача, «Анализы», страница анализа, «Выбранные анализы».

### Маршруты

| Экран | Маршрут | Контекст записи |
|---|---|---|
| Услуги и цены | `/services?q=…&category=…` | «Записаться» у услуги → `/booking?service=<id>` |
| Страница услуги | `/services/[id]` | Общая кнопка → `/booking?service=<id>`; у врача → `/booking?service=<id>&doctor=<id>` |
| Врачи | `/doctors?q=…&category=…` | → `/booking?doctor=<id>` |
| Страница врача | `/doctors/[id]` | Общая кнопка → `/booking?doctor=<id>`; у услуги → `/booking?service=<id>&doctor=<id>` |
| Анализы | `/lab?q=…&category=…` | Выбор анализов, панель → `/booking/lab` |
| Страница анализа | `/lab/[id]` | «Добавить к записи» — в выбранные |
| Выбранные анализы | `/lab/selected` | «Выбрать дату и время» → `/booking/lab` |

Неизвестный id → `notFound()`, ответ 404. Все ссылки собираются в `src/lib/routes.ts`.

### Как устроено

- **Данные.** Один канонический набор на сущность (PD-25): `src/data/mock/{services,doctors,analyses,categories}.ts`. Страницы получают данные только через `src/services/{services-catalog,doctors,analyses}.ts`.
- **Цена врача.** «от …» на карточке = цена его основного приёма (первая услуга в `doctor.services`) — вычисляется, не дублируется. На странице услуги карточка врача показывает его цену именно за эту услугу.
- **Поиск и направления.** Фильтрация на клиенте, мгновенно, без запросов к серверу (`src/lib/use-catalog-filters.ts`). Запрос и направление синхронизируются с адресом через `history.replaceState`: ссылкой можно поделиться, после обновления фильтр сохраняется. Прямой заход на `/services?q=терапия` применяет запрос сразу при серверной отрисовке (PD-23). Поиск по услугам учитывает название направления.
- **200+ позиций.** Показывается по 20 строк (врачей — по 9), «Показать ещё» добавляет следующую порцию. Счётчики направлений учитывают поисковый запрос.
- **Выбранные анализы.** `src/lib/selected-analyses.ts` — хранилище без библиотек на `useSyncExternalStore`, в `localStorage` лежат только id. Цены и подготовка всегда берутся из каталога. Сохраняется между страницами и после обновления, синхронизируется между вкладками. С CRM не связано.
- **Закреплённые панели.** Панель выбранных анализов (`SelectedAnalysesBar`) и mobile-панель действия (`StickyActionBar`) — `position: sticky` последним элементом содержимого: при прокрутке прилипают к низу экрана, в конце — занимают своё место в потоке и не перекрывают последнюю строку и подвал. Mobile-панель появляется, только когда основная кнопка страницы ушла с экрана.
- **Загрузка.** `loading.tsx` в `/services`, `/doctors`, `/lab` — скелетон строк, как состояние «Loading» в макетах.

### Для разработчика

- `cn()` в `src/lib/cn.ts` только склеивает классы и **не разрешает конфликты** Tailwind. Не переопределяйте базовые классы компонента через `className` (например, `px-4` поверх `px-5`) — результат зависит от порядка CSS. Нужен другой вид — добавьте вариант (`size`, `variant`, `multiline`).
- В dev-режиме Turbopack иногда не подхватывает Tailwind-классы из **новых** папок маршрутов. Если стили не применились — остановить dev-сервер, удалить `.next`, запустить снова. Production-сборка не затронута.

## 14. Запись — решения и открытые вопросы

Реализовано 2026-09-26: запись к врачу (`/booking`) и на анализы (`/booking/lab`). CRM и настоящие смс не подключены.

### Точки входа

| Откуда | Адрес | Старт | Отмечено пройденным |
|---|---|---|---|
| «Записаться» в шапке, на главной | `/booking` | Услуга | — |
| Страница услуги | `/booking?service=<id>` | Врач | Услуга |
| Страница врача | `/booking?doctor=<id>` | Услуга (только услуги врача) | Врач |
| Услуга в профиле врача | `/booking?service=<id>&doctor=<id>` | Дата и время | Услуга, Врач |
| Быстрый слот на странице врача | `/booking?doctor=<id>&date=…&time=…` | Услуга → время резервируется само | Врач |
| «Перейти к записи» / «Выбрать дату и время» | `/booking/lab` | Дата и время | Анализы |

Параметрам адреса не доверяем: неизвестная услуга или врач, врач без этой услуги, неверная дата — понятное сообщение и нужный шаг, без падения.

### Как устроено

- **Сервис записи** — `src/services/booking/`: контракт `BookingService` (`getAvailability`, `getUpcomingDays`, `reserveSlot`, `releaseReservation`, `sendOtp`, `verifyOtp`, `createAppointment`) и MOCK-реализация. Переключение на CRM — одна строка в `booking/index.ts`. HTTP-эндпоинтов нет.
- **Расписание (MOCK)** — `src/data/mock/availability.ts`: недельные правила для каждого врача и отдельное расписание процедурного кабинета. Занятость слотов детерминирована. Из этого же источника берутся «Ближайшее время» на карточках врачей (`src/services/availability.ts`), быстрые слоты на странице врача и превью записи на главной. Статичных подписей «Сегодня, 14:20» в данных больше нет.
- **Черновик записи** — `src/lib/booking-draft.ts`, sessionStorage вкладки. Id черновика в адресе (`?draft=…`): обновление страницы возвращает на тот же шаг, новый вход по ссылке начинает новую запись. Хранятся только выбор, имя и телефон — медицинских данных нет.
- **Резерв 5 минут** — после выбора времени. Таймер обновляется каждую секунду, скринридеру объявляется только «осталась 1 минута». По истечении (в том числе после обновления страницы) — возврат к выбору времени с сообщением; услуга и врач сохраняются.
- **Код подтверждения (MOCK)** — 5 цифр, как в макете; тестовый код `11111`. Подпись «Демо-код: 11111» — только при `NEXT_PUBLIC_DEMO_MODE=true` (PD-26), по умолчанию скрыта. После подтверждения номер помнится до закрытия вкладки — повторно код не спрашивается («Вы вошли как …»).
- **Запись на анализы** использует то же хранилище выбранных анализов. После записи список очищается, состав показан на экране «Вы записаны».
- **Сценарии для проверки** (sessionStorage `smlab:mock-scenario`): `availability-error`, `taken-on-reserve`, `taken-on-confirm`, `short-reservation` (резерв 20 секунд).

### Решения при реализации

| Что | В макете | В коде | Почему |
|---|---|---|---|
| Код из смс | 5 ячеек | 5 ячеек, тестовый код `11111` | Макет — источник вида; «1111» в задаче — пример |
| Степпер записи на анализы | 4 шага, «Анализы» пройден | Так же; если список пуст — «Анализы» текущий, дальше не пройти | Экран выбора анализов уже утверждён (`/lab/selected`) |
| Подписи будущих шагов, дни без времени | `ink-400` (3.01) | `--color-step-upcoming-fg` (4.52) | Текст 14–15px должен проходить 4.5 |
| Быстрые слоты на странице врача | Выбор слота на месте | Слот — ссылка в запись с этим временем | Резерв и выбор даты — часть записи (закрыт вопрос 1 раздела 13) |
| Дни без свободного времени | Недоступны | Можно выбрать — показывается ближайшая дата с кнопкой | Состояние «Нет свободного времени на дату» из макета |
| После проверки кода | Проверяется автоматически | Автопроверка + кнопка «Продолжить», фокус на ней | Без неожиданной смены экрана |
| «Перейти в личный кабинет» | Кабинет | `/account` — заглушка | Кабинет — следующий этап |
| Главная | Статическая | Собирается на каждый запрос | «Ближайшее время» зависит от текущего момента |
