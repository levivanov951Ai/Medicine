## 4. Architecture

- Один процесс `uvicorn` на `0.0.0.0:8000`, **HTTP без TLS**, доступ «с других компьютеров в сети» по IP (`ЧИТАЙ_МЕНЯ.txt`).
- Роли: `sysadmin`, `admin` (регистратура), `doctor` (кабинет врача). Пациентского портала нет.
- `/uploads` и `/reports` раздаются как статические папки.
- Время — «наивное» локальное время ПК (`date.today()` / `datetime.now()`, ~50 мест), часовые пояса не используются.

## 8. Authentication

- Сессионная cookie Starlette (`SessionMiddleware`), подписывающий ключ **прописан в коде**.
- Вход персонала: выбор пользователя из списка + пароль; хэш **SHA-256 без соли**; дополнительно пароль хранится **открытым текстом** (`users.password_plain`) и выводится в HTML страницы пользователей.
- Кабинет врача (`/cabinet/login`): у врача без пароля вход без пароля; в текущей базе пароли врачей не заданы.
- Ни API-ключей, ни JWT, ни OAuth. API для браузера сайта или server-to-server **не предусмотрен** — это внутренняя система для персонала в локальной сети.

- Рабочее время — одно на врача для всех дней: `work_start`, `work_end`, шаг `step_minutes`, длительность `appointment_minutes`.

## 21. Integration gaps

1. Нет интеграционного API и аутентификации для внешней системы.
2. Нет свободных слотов как данных, нет расписания по дням и исключений.
3. Нет резерва слота и надёжной защиты от двойной записи.
4. Нет связи врач ↔ услуга и цены у врача.
5. Нет лабораторного каталога (срок, подготовка, биоматериал), комплексов, акций.
6. Нет полей врача для сайта (стаж, описание, фото).
7. Нет OTP/СМС; пациент не нормализован по телефону, дубли не контролируются.
8. Нет правил отмены/переноса, нет `cancelledAt` и источника записи.
9. Система в локальной сети, HTTP, без авторизации на большинстве действий — публичный сайт к ней напрямую подключать нельзя.
10. SQLite и один процесс — одновременная запись с сайта и регистратуры требует аккуратной блокировки.

## 23. Recommended integration strategy

1. **Не подключать сайт к текущей CRM напрямую.** Сначала — безопасность CRM: подключить проверку авторизации на всех маршрутах, убрать `password_plain`, соль/современный хэш, ключ сессии из окружения, закрыть `/uploads`, HTTPS, не выставлять в интернет.
2. **Отдельный интеграционный API в CRM** (минимальный, server-to-server, ключ в заголовке, только из сервера Next.js):
   `GET services`, `GET doctors`, `GET doctor-services`, `GET availability?doctorId&serviceId&from&days`, `POST holds`, `DELETE holds/{id}`, `POST appointments` (идемпотентно, с проверкой пересечений в транзакции), `GET patients/{id}/appointments`, `POST appointments/{id}/cancel`, `POST appointments/{id}/move`, `POST patients/find-or-create` (по нормализованному телефону). Записи с сайта — с меткой источника.
3. В CRM добавить данные: расписание по дням и исключения, связь врач ↔ услуга, поля сайта для врача; каталог анализов — либо поля в CRM, либо контент сайта.
4. Контент, которого в CRM нет (акции, комплексы, описания, фото, подготовка к анализам), оставить на стороне сайта.
5. OTP — отдельный СМС-провайдер на сервере Next.js (CRM не умеет).
6. На стороне сайта — адаптер `DATA_SOURCE=crm` по существующим контрактам сервисов, только после появления API (см. `CRM_INTEGRATION.md`, раздел 13).
