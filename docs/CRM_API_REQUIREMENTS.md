# CRM API Requirements — СМЛаб ↔ «МедЦентр»

_2026-10-03. **Это требования, а не документация.** API в CRM «МедЦентр» сейчас нет (`CRM_AUDIT.md`, раздел 7). Здесь описано, какие возможности нужно добавить в CRM или в отдельный серверный адаптер к её базе, чтобы подключить сайт. Названия методов и форматы — решение разработчика CRM; ниже — capabilities и правила. Контракты сайта — `CRM_INTEGRATION.md` (R1–R11, W1–W10)._

## 1. Target architecture

```
Browser (сайт СМЛаб)
   │  HTTPS, только сессия пациента (httpOnly cookie)
   ▼
Next.js server (СМЛаб)            ← хранит ключ к CRM API, проверяет пациента
   │  HTTPS / VPN, ключ сервиса, server-to-server
   ▼
CRM API или CRM adapter           ← авторизация сервиса, валидация, транзакции
   │
   ▼
medcenter.db (SQLite)             ← рабочая база, остаётся в клинике
```

Правила:

- **Браузер никогда не обращается к CRM напрямую** и не получает ключи CRM.
- Рабочий Windows-компьютер клиники **не открывает порт 8000 в интернет**. Доступ сайта — через отдельный API/адаптер с HTTPS и, желательно, через VPN или туннель с ограничением по IP сервера сайта.
- API для сайта — отдельный набор методов с собственной авторизацией, а не HTML-маршруты интерфейса персонала.
- Только минимально необходимые данные: сайт не получает медицинские протоколы, паспортные данные, оплаты.
- Все времена — в часовом поясе клиники **`Europe/Moscow`** (PD-30), формат `YYYY-MM-DD` + `HH:MM` или ISO 8601 со смещением.
- SQLite + несколько писателей (регистратура и сайт): операции записи — в транзакции с проверкой конфликта.

## 2. Catalog

| Capability | Обязательно | Поля (минимум) | Примечание |
|---|---|---|---|
| Направления / специальности | да | id, name | сейчас — `doctor_groups` и строка `services.category_name` |
| Услуги | да | id, code, name, categoryId, price, durationMinutes, isActive | только активные; `description` — желательно |
| Цены услуг | да | serviceId, price | одна цена или цена у врача |
| Врачи | да | id, ФИО, specialtyIds, isActive | для сайта также: стаж, описание, фото (сейчас нет) |
| Связь врач ↔ услуга | **да** | doctorId, serviceId, price?, durationMinutes? | сейчас отсутствует |
| Цена услуги у врача | если цены различаются | doctorId, serviceId, price | решение владельца |
| Анализы | да | id, code, name, price, isActive | срок, подготовка, биоматериал — в CRM нет; или добавить, или вести на сайте |
| Комплексы | если появятся | id, name, analysisIds, price | сейчас нет сущности |
| Акции | если CRM станет источником | id, title, conditions, validUntil, target | сейчас нет; иначе — контент сайта |
| Сведения о клинике | да | телефон, адрес, режим работы | частично в настройках |

Требования: стабильные id; признак активности; изменение данных отражается в API без ручных выгрузок.

## 3. Availability

CRM (или адаптер) должна **сама вычислять свободные слоты** — сайт не должен восстанавливать расписание по сырым записям.

Нужна модель расписания:

- рабочие дни недели врача;
- рабочие часы по дням (могут различаться);
- перерывы;
- выходные и праздники клиники;
- исключения (разовые изменения часов);
- отпуска / отсутствие врача;
- шаг сетки и длительность приёма — с учётом услуги (`durationMinutes`), если она отличается от длительности врача;
- существующие записи (статусы, кроме `cancelled`) и активные резервы;
- отдельное расписание забора анализов (процедурный кабинет / ответственный сотрудник).

Capability: **«свободные слоты»** — вход: врач + услуга (или забор анализов), дата начала, число дней; выход: дни со списком `HH:MM` и признаком «свободно». Желательно — пакетный запрос «ближайший свободный слот» для списка врачей (карточки каталога).

Часовой пояс — `Europe/Moscow`. Нужно подтвердить, что компьютер с CRM работает в этом поясе (сейчас CRM использует локальное время ПК).

## 4. Reservation

Нужен механизм временного удержания слота:

| Capability | Требование |
|---|---|
| Reserve slot | атомарно проверяет, что интервал свободен (пересечения, а не только время начала), и создаёт резерв |
| Reservation id | возвращается сайту |
| Expiration | срок жизни резерва; резерв перестаёт блокировать слот после истечения |
| Release | снять резерв досрочно |
| Confirm | создание записи по id резерва |
| Conflict detection | ответ «занято» при пересечении с записью или чужим резервом |

Сейчас сайт показывает таймер **5 минут** — это демо-решение PD-02. **Срок резерва для production должен подтвердить владелец.** Если резерв в CRM не реализуют — запись создаётся сразу, а таймер на сайте убирается (см. `CRM_INTEGRATION.md`, раздел 6).

## 5. Appointments

| Capability | Требование |
|---|---|
| Create | врач, услуга(и), дата, время (или id резерва), пациент; CRM сама фиксирует цену и длительность; метка источника «сайт» |
| Create (анализы) | набор анализов, дата, время; как записывать без врача — решить в CRM |
| List for patient | только записи этого пациента |
| Details | одна запись, только если принадлежит пациенту |
| Cancel | статус «отменена», время отмены, причина отказа, если нельзя |
| Reschedule | атомарно: новое время занято → старое освобождено |
| Status | `scheduled`, `completed`, `cancelled`, `no_show` (существуют в CRM) + понятное «можно отменить / перенести и почему нет» |
| Idempotency | повтор запроса (двойной клик, повтор после таймаута) не создаёт вторую запись |
| Conflict protection | проверка пересечения интервалов в транзакции |

Правила отмены и переноса — **от владельца** (сейчас PRODUCTION RULE UNKNOWN, PD-06). Проверка правил — на стороне CRM/адаптера, не только в интерфейсе сайта.

## 6. Patients

| Capability | Требование |
|---|---|
| Lookup | по **нормализованному** телефону (10 цифр после +7) |
| Create | ФИО (или имя), телефон |
| Update | только базовый профиль (имя) |

**Не включать** в API сайта медицинские протоколы, диагнозы, документы, паспортные данные, оплаты — без отдельного решения и правового основания.

## 7. Authentication

Две разные задачи:

**Сайт ↔ CRM (сервис):**
- ключ или токен сервиса, хранится только на сервере Next.js (переменная окружения, не `NEXT_PUBLIC_*`);
- ротация ключа, отзыв, журнал обращений;
- HTTPS; ограничение по IP / VPN.

**Пациент ↔ сайт:**
- смс-провайдер — выбрать (в CRM его нет);
- запрос кода (отправка, повтор не чаще N секунд, лимиты);
- проверка кода (срок жизни, лимит попыток);
- после проверки — серверная сессия сайта (httpOnly, Secure, SameSite cookie);
- patientId берётся из сессии, а не из запроса браузера.

Учётные данные CRM браузеру не передаются никогда.

## 8. Non-functional

- Время ответа «свободных слотов» — достаточное для каталога (решить после замера).
- Ошибки — понятные коды: «занято», «резерв истёк», «нельзя отменить», «не найдено», «сбой».
- Тестовая среда с обезличенными данными до любых работ с рабочей базой.
- Версионирование API.
