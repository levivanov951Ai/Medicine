## 1. Классификация данных

В проекте любая единица информации обязана иметь один из четырёх статусов. Статус указывается явно — в коде, в макетах, в контенте.

| Статус | Значение | Как использовать |
|---|---|---|
| **FACT** | Подтверждённая заказчиком информация | Можно публиковать как сведения о клинике |
| **PRODUCT DECISION** | Продуктовое или UX-решение, принятое командой в рамках делегированных полномочий | Обязательно к исполнению наравне с FACT. Может быть пересмотрено владельцем продукта |
| **MOCK** | Временные данные исключительно для визуального прототипа | Только внутри прототипа, всегда с явной пометкой. Не является сведениями о клинике |
| **UNKNOWN** | Информация, которую заказчик ещё не предоставил | Заменяется placeholder-ом вида `[Телефон]` |

**MOCK и UNKNOWN никогда не превращаются в реальные сведения о клинике.**

## 2. FACT — подтверждённая информация

### 2.1 О клинике

| Параметр | Значение |
|---|---|
| Название | Смлаб |
| Количество филиалов | Один |
| Адрес | Западный обход, 42к2 |

### 2.2 Бренд и визуальный стиль

**Основные брендовые цвета:**
- розовый;
- голубой.

**Визуальный стиль:** современная частная медицина — светлый интерфейс, профессиональный, спокойный, чистый, дружелюбный.

### 2.3 Главные задачи сайта

1. Запись пациента на медицинскую услугу.
2. Поиск информации об анализах.
3. Запись на сдачу анализов.
4. Авторизация пациента и личный кабинет.

### 2.4 Базовые правила записи

- Пациент выбирает врача **самостоятельно**. Автоподбор врача не предусмотрен.
- Пациент выбирает конкретное доступное время **самостоятельно**.
- После успешной записи выбранный временной слот **становится недоступен** другим пользователям.
- Запись **подтверждается сразу**.
- Обязательные данные при записи: **имя** и **номер телефона**.
- Авторизация пациента **необходима**.

**Это НЕ заявка на обратный звонок.** Запрещены формулировки и любые их варианты:

- ❌ «Администратор свяжется с вами»
- ❌ «Ожидайте подтверждения»
- ❌ «Мы перезвоним вам для подтверждения»
- ❌ «Заявка принята» (в значении «ещё не запись»)

Корректная формулировка результата — факт состоявшейся записи (например: «Вы записаны»).

### 2.5 Анализы

Доступна запись на сдачу анализов. Для анализа пациент должен иметь возможность увидеть:

- название;
- цену;
- срок выполнения;
- информацию о подготовке;
- действующие акции;
- возможность записаться.

### 2.6 CRM

CRM **уже существует** и будет интегрирована **позднее**, на финальном этапе.

## 3. PRODUCT DECISIONS

Решения приняты командой 2026-09-21 в рамках делегированных владельцем продукта полномочий. Обязательны к исполнению наравне с FACT.

### PD-01. Авторизация — OTP по номеру телефона

Отдельного сложного процесса регистрации не существует.

**Сценарий:** номер телефона → код подтверждения → пользователь авторизован.

- Новый пользователь: профиль создаётся **автоматически** после подтверждения телефона.
- Существующий пользователь: вход в существующий профиль.
- Авторизация **обязательна для завершения записи**.
- Данные первой записи (имя, телефон) сохраняются и **автоматически подставляются** при последующих записях.

**Ограничение:** OTP фиксируется как **продуктовый сценарий**. Конкретный SMS-провайдер и техническая реализация отправки кода **не проектируются**.

### PD-02. Конфликт временных слотов — резерв на 5 минут

После выбора конкретного времени слот **временно резервируется на 5 минут**.

- В интерфейсе отображается статус резерва и обратный отсчёт (например: «Время зарезервировано на 05:00»).
- Завершение записи → слот окончательно занят.
- Истечение 5 минут без завершения → слот снова доступен.

**Ограничение:** это UX/product rule. Техническая реализация блокировок, транзакций и concurrency **не проектируется**.

### PD-03. Запись к врачу — 5 логических этапов, не 7

```
1. Услуга
2. Врач
3. Дата и время        ← один логический этап
4. Данные / подтверждение телефона
5. Подтверждение записи
```

- Дата и время — **один этап**, один экран.
- Для авторизованного пользователя этап 4 **практически пропускается**, данные подставляются автоматически.

**Адаптация под точку входа — пользователь не выбирает повторно то, что системе уже известно:**

| Точка входа | Маршрут |
|---|---|
| Страница врача | Врач известен → услуга этого врача → дата и время → подтверждение → запись |
| Страница услуги | Услуга известна → врач → дата и время → подтверждение → запись |
| Общий вход | Услуга → врач → дата и время → подтверждение → запись |

### PD-04. Анализы — множественный выбор

Пациент может выбрать **несколько анализов одновременно**.

**Механизм:** список выбранных исследований. Допустимые названия — «Выбранные анализы», «Мои анализы». Агрессивная ecommerce-терминология («корзина», «оформить заказ», «checkout») не используется.

**Возможности пользователя:** добавить анализ, удалить анализ, видеть итоговую стоимость, открыть информацию о подготовке, перейти к записи.

**Flow:** поиск / каталог анализов → выбранные анализы → дата и время → данные / авторизация → подтверждение → запись.

**Требование к лёгкости:** при выборе **одного** анализа пользователь **не должен** взаимодействовать с отдельным сложным списком. UX максимально лёгкий.

### PD-05. Пакеты и check-up программы

Предусматриваются готовые комплексы анализов. Это **отдельная сущность интерфейса**, относящаяся к каталогу анализов. Пакет может содержать несколько исследований.

**Пользователь может:** посмотреть состав, стоимость, выгоду (если она реально предоставляется), подготовку, добавить весь комплекс в выбранные анализы.

**Ограничение:** реальные пакеты Смлаб не придумываются. Для прототипа — MOCK.

### PD-06. Отмена и перенос записи

В личном кабинете пользователь может: посмотреть запись, отменить запись, перенести запись.

**Состояния записи, обязательные в дизайне:**
- Предстоящая
- Завершена
- Отменена

**Перенос:** текущая запись → выбор новой даты и времени → подтверждение переноса.

**Ограничение:** конкретное временно́е ограничение (вида «не позднее чем за 24 часа») **сейчас не фиксируется**. Правило должно быть настраиваемым в будущем. В дизайне не допускается захардкоженная формулировка срока.

### PD-07. Каталог услуг — масштабируемый

Интерфейс проектируется под **20–200+ услуг**. Проектирование исходя из предположения, что услуг мало, **запрещено**.

**Обязательно:** поиск, категории, понятная иерархия, быстрый переход к услуге, цена, возможность записи.

### PD-08. Цены — без отдельной страницы

Отдельная страница «Цены» **не создаётся**. Раздел называется **«Услуги и цены»**.

Цены отображаются непосредственно: в каталоге услуг, на странице услуги, на странице врача, в каталоге анализов, на странице анализа.

Пользователь не должен переходить на отдельную страницу, чтобы узнать стоимость.

### PD-09. Результаты анализов — не в первой версии

В первой версии личного кабинета результаты анализов **не показываются**.

**Не проектируются:** медицинские документы, лабораторные результаты, диагнозы, назначения, рецепты, медицинская карта.

Возврат к вопросу возможен только после понимания возможностей CRM, требований безопасности и правил хранения медицинских данных.

### PD-10. Семейные профили — не в первой версии

Ведение детей и родственников из одного аккаунта **не добавляется**. Проектируется аккаунт **одного пациента**. Архитектурные заделы под семейные аккаунты сейчас не нужны.

### PD-11. Оплата — только в клинике

Онлайн-оплата в первой версии **не предусматривается**. На сайте отображается стоимость, расчёт происходит в клинике.

**Не добавляются:** банковские карты, checkout, предоплата, СБП, сохранённые способы оплаты.

### PD-12. Выезд на дом — не предусматривается

Выезд медицинского сотрудника на дом **не добавляется** ни в sitemap, ни в интерфейс.

### PD-13. Акции — три типа привязки

Акция может быть связана с: **услугой**, **анализом**, **комплексом анализов**. UI обязан поддерживать все три варианта.

**Ограничение:** реальные акции Смлаб не придумываются. MOCK исключительно для демонстрации UI.

### PD-14. Личный кабинет — максимально простой

```
/account          ближайшая запись; будущие записи; прошедшие записи
/account/profile  имя; телефон; базовые персональные данные (на будущее)
```

Отдельный сложный медицинский портал **не создаётся**.

### PD-15. Структура верхнего уровня

Главная · Услуги и цены (каталог → страница услуги) · Врачи (каталог → страница врача) · Анализы (каталог → страница анализа → комплексы/check-up) · Акции · О клинике · Контакты · Запись · Авторизация · Личный кабинет · Юридические страницы.

Это **направление**, а не требование сохранить конкретные URL. Изменение routing допустимо при наличии UX-обоснования.

### PD-16. Главная страница — сервисная, не рекламная

Два главных пользовательских намерения доступны практически сразу:
- «Записаться к врачу»
- «Сдать анализы»

**Запрещено:** hero высотой в весь экран с одной рекламной фразой.

**Обязателен быстрый вход в:** поиск услуги, запись, поиск анализа.

После первого экрана допустимы: основные направления, популярные услуги, анализы, врачи, акции, преимущества, информация о клинике, контакты.

**Правило отбора блоков:** блок не добавляется только потому, что он обычно встречается на сайтах клиник. Каждый блок обязан иметь обоснование.

### PD-17. Mobile first check

Основной desktop frame — **1440 px**. Критические сценарии **отдельно** проектируются для **390 px**:

поиск услуги · поиск анализа · выбранные анализы · выбор врача · календарь · выбор временного слота · OTP · личный кабинет.

### PD-18. Правило против галлюцинаций

Используются статусы: **FACT**, **PRODUCT DECISION**, **MOCK**, **UNKNOWN**.

MOCK-данные не превращаются в фактические сведения о Смлаб. Если для дизайна необходим текст, врач, анализ, цена или акция, которых нет, используется реалистичный MOCK с явной фиксацией временного статуса.

### PD-19. Источники истины и разрешение конфликтов

При расхождении между документами приоритет определяется **типом информации**, а не свежестью документа:

| Тип информации | Источник истины |
|---|---|
| Продуктовая логика, реальные факты о клинике | `PROJECT_CONTEXT.md` (этот файл) |
| Визуальный дизайн | Финальный Claude Design artifact |
| Точные design tokens | `design/tokens.css` — извлечены из финального Design System и экранов |
| Структура компонентов, states, responsive, interactions | `docs/DEVELOPER_HANDOFF.md` |
| Дополнительный UX-контекст | `DESIGN_BRIEF.md` |

**Частный случай, уже возникший:** при расхождении цветов между Developer Handoff и финальным Claude Design используются значения из **финального Claude Design**.

**Правило против повторения конфликта:** в проекте существует **один канонический набор design tokens** — `design/tokens.css`. Значения токенов не дублируются ни в одном другом файле. Остальные документы ссылаются на **имена** токенов.

### PD-20. MOCK — внутренний статус, невидимый в интерфейсе

**MOCK — это статус данных для разработки, а не элемент интерфейса.**

- В пользовательском интерфейсе **никаких видимых бейджей, меток или надписей «MOCK» быть не должно.**
- Разделение обеспечивается в **коде и документации**: mock-данные лежат в отдельных изолированных файлах, помеченных как временные, и удаляются одним действием при подключении CRM.
- Mock-данные **не выдаются за реальные сведения клиники** — ни в текстах, ни в метаданных страниц.

**Отменяет** требование раздела 10 `DESIGN_BRIEF.md` о визуальной пометке mock-данных компонентом MOCK badge в интерфейсе.

### PD-21. Смена номера телефона — FUTURE

Смена номера через повторный OTP **не является подтверждённой функцией MVP**.

На текущем этапе:

- в профиле **отображается** текущий номер пользователя;
- функциональная смена номера **не реализуется**;
- дополнительная auth-логика ради неё **не создаётся**.

Статус: **FUTURE / PRODUCT ASSUMPTION**. Возврат к вопросу — после подключения реальной авторизации.

## 7. Правила работы с данными

### 7.1 Запрещено придумывать как реальные факты

- врачей клиники;
- награды;
- лицензии;
- отзывы;
- статистику;
- количество пациентов;
- медицинские гарантии;
- скидки;
- телефоны;
- цены;
- медицинские рекомендации.

### 7.2 Когда использовать MOCK, а когда placeholder

- **Placeholder** (`[Цена]`) — по умолчанию. Применяется, когда пустое поле не мешает оценить интерфейс.
- **MOCK** — только когда без наполнения невозможно оценить вёрстку и поведение интерфейса (сетка карточек врачей, календарь со слотами, список анализов, состав пакета).

### 7.3 Требования к MOCK-данным

- Все mock-данные хранятся **отдельно** от кода интерфейса, в изолированных файлах, чтобы их можно было удалить одним действием при подключении CRM.
- Каждый mock-набор содержит явную пометку о том, что это временные данные прототипа.
- Mock-данные **не помечаются визуально в интерфейсе** (PD-20). Разделение обеспечивается на уровне кода и документации, а не бейджами на экране.
- Mock-имена врачей должны быть очевидно условными и не совпадать с именами реальных людей.
